When memories fade - skills after compaction

An investigation into what happens to skills after compaction and if they are refreshed.

Sam Saccone · October 17, 2026

When a harness loads and injects a skill, the agent has full skill context.

While external research has analyzed model performance degradation as context bloat increases, there is a gap in published understanding about degradation due to the truncation/compaction of skills. When a harness compacts long-running conversations due to token limits, working "memory" is dropped. When the user asks the harness to perform another task requiring a previously loaded skill, the memory of the skill has faded and it is unclear IF the agent will know about the memory loss and will refresh its memory.

Exploring and understanding this specific degradation mode in detail across harnesses and models—who re-loads the skill, who hallucinates, and how harness engineering dictates the outcome—is what this post aims to explore.

It turns out what happens next is determined almost entirely by harness architecture. Across six major runtimes and hundreds of multi-turn trials, two takeaways emerged:

  1. Avoid the compaction summary trap: Compaction must never hint that a skill was previously used without explicitly stating that its instructions were unloaded and must be re-read. When a summarizer casually notes that a skill was invoked earlier, models assume the procedural rules are still active in context, bypass the reload tool, and immediately hallucinate.
  2. An active ledger bridges the skill reloading gap between thinking and low/no-thinking models: Thinking models can catch their own missing context and re-read documentation. Low/no-thinking and lightweight models cannot, they collapse into hallucination unless the harness maintains an Active Skill Ledger that explicitly tells them which skills were active and must be re-hydrated.

The Solution: The Active Skill Ledger

To bridge the performance divide across models, the harness must manage skill retention explicitly:

  1. When an agent invokes a skill during a session, the runtime records that skill ID in session metadata.
  2. When the compaction engine truncates the conversation history, the harness preserves those active skill IDs in the compaction checkpoint.
  3. In the post-compaction system prompt or first subsequent turn, the harness injects a lightweight re-hydration preamble:
Active Skill Ledger System Preamble
1 <active_skills>
2 The following skills were activated earlier in this session. You must re-read their instructions if your current task involves their workflows:
3 - pbj_sandwich_probe (location: .agents/skills/pbj_sandwich_probe/SKILL.md)
4 </active_skills>

This injection costs fewer than 50 tokens and provides the exact cognitive signal that low/no-thinking models require to re-read documentation instead of guessing.

Who Excels and Who Suffers

To measure what actually happens across the ecosystem today without this ledger, I built a multi-turn evaluation benchmark and ran it across six major agent runtimes—Vercel FX (fx), Pi Coding Agent (pi), OpenCode (opencode), OpenAI Codex (codex), Grok Build (grok), and Reflection AI Mirror (mirror)—comparing reasoning models against low/no-thinking models across hundreds of multi-turn trials.

The benchmark exposed a large gap between runtimes:

  • Who is doing the best:
    • OpenCode 2.0 is the standout performer across our entire suite. By explicitly defining <skill_content> lifecycle boundaries in its preamble, enforcing strict compaction boundaries (leaving an unambiguous procedural vacuum with 0% confusing debris), and aligning its tool schemas 1:1, OpenCode 2.0 achieved 100% reload awareness with reasoning models and was the only harness where low/no-thinking completion models (gpt-4.1-nano) achieved any post-compaction success (30% probe pass rate).
    • Vercel FX and Pi Coding Agent deliver near-perfect awareness with reasoning models (100% reload detection) because their system prompts treat skill checking as an imperative obligation ("Before substantive work, load each selected skill..."). But they stumble on execution with smaller models, where dumping raw markdown into context causes a 100% syntax parse failure rate.
  • Who is suffering the most:
    • OpenAI Codex suffered from complete procedural blindness. Because its system prompt lacks an imperative instruction to inspect skills before execution, smaller models like gpt-4o-mini suffered from a 100% Blind Hallucination Rate across both Turn 1 and Turn 3, never checking SKILL.md once in the entire session and relying entirely on parametric hallucinations.
    • Reflection AI Mirror suffered the worst degradation under smaller models: 0% baseline discovery, 100% Blind Hallucination, and aggressive safety filters that triggered false-positive prompt injection defenses against esoteric culinary parameters even with full context retention.
    • Grok Build's voluntary prompt framing ("When you recognize that a task matches...") caused gpt-4.1-nano to skip skills in 9 out of 10 trials (90% Blind Hallucination), while imposing a defensive Redundant Reload Tax under uncompacted conditions.
    • OpenCode 1.x serves as a counter example: before its 2.0 rewrite, catalog-to-tool schema mismatches caused models to suffer a catastrophic 100% Blind Hallucination Rate.

Which brings us to the core metrics we use throughout this investigation:

Compaction Skill Survival Rate (CSSR)

Definition: The percentage of exact procedural instruction needles (CLI flags, schemas, negative constraints) that survive in the active LLM context window post-compaction.

Epistemic Awareness Rate (EAR)

Definition: The percentage of post-compaction trials where an agent detects that its procedural working memory was evicted and actively re-reads the skill file before touching code.

Blind Hallucination Rate (BHR)

Definition: The percentage of trials where an agent proceeds directly into execution without re-reading the evicted skill, guessing flags and parameters from parametric memory.

Skills Are Ephemeral State

Before looking at the benchmark numbers, we have to look at how modern agent engines treat skills under the hood. Skills are not permanent cognitive capabilities. They are temporary, ephemeral text entries inside a running transcript.

Across all six harnesses evaluated:

  1. Vercel FX (fx): Renders <available_skills> in the system prompt with strict guidance ("Before substantive work, load each selected skill that is not already supplied as explicit skill content"). When compaction triggers (via fx-compactor-v1 or token limits), past tool outputs—including the loaded skill text—are folded into summary handles.
  2. Pi Coding Agent (pi): Follows the Agent Skills spec. The system prompt advertises <skills><available_skills> with file locations. Compaction inserts a compaction node that evicts earlier turns from the active prompt sent to the LLM.
  3. OpenCode (opencode): Discovers skills in .opencode/skills/<name>/SKILL.md. The harness supplies a native skill tool that pulls markdown into conversation entries.
  4. OpenAI Codex (codex): Discovers skills across .agents/skills/<name>/SKILL.md and .codex/skills/. Compaction folds thread history.
  5. Grok Build (grok): Discovers skills with a multi-tier hierarchy: local CWD (./.grok/skills/), parent repos up to root (<repo_root>/.grok/skills/), .agents/skills/, user global (~/.grok/skills/), and backward compatibility with Claude (.claude/skills/) and Cursor (.cursor/skills/). Grok compiles skills into a Jinja-templated <available_skills> prompt block rendered alongside its native tool descriptions in crates/codegen/xai-grok-grove-dataplane/src/skills.rs.
  6. Reflection AI Mirror (mirror): Discovers skills at .agents/skills/<name>/SKILL.md and .claude/skills/<name>/SKILL.md, injecting them into <available_skills>. When compacted, Mirror appends a ContextWindowRecord with a Compaction summary payload, and subsequent turns crop all history before that record.

How Skill Hinting Differs Across Runtimes

The runtimes diverge sharply in how strongly they instruct the LLM to inspect skills:

  • Explicit Mandatory Pre-Condition (Vercel’s FX & Pi):

Both FX and Pi frame skill inspection as an imperative obligation before touching code:

  • FX: "Before substantive work, load each selected skill that is not already supplied as explicit skill content."
  • Pi: "Use the read tool to load a skill's file when the task matches its description."

This explicit pre-condition provides enough cognitive activation to prompt generalist models like gpt-4o to re-read skills even after compaction wipes their memory.

  • Voluntary (Grok Build & Reflection AI Mirror):

Both Grok Build and Reflection AI Mirror advertise available skills and point the agent toward inspection tools (read_file, use_tool, or read). However, they frame skill loading around recognition or optional discovery:

  • Grok: "When you recognize that a task matches one of the available skills listed below, use this tool to load the full skill instructions."
  • Mirror: "Available skills are located in .agents/skills/<name>/SKILL.md. To inspect skill documentation, use the read tool."
  • Passive Catalog Exposure (OpenCode 1.x & Codex):

OpenCode 1.x and Codex expose skill definitions or directory structures passively in the tool schema or directory tree with minimal or zero behavioral nudges.

When context is compacted, the skill is wiped from active memory. The agent is left with only the high-level description in its system prompt and a vague summary of Turn 1.

The PB&J Challenge

Here is where standard benchmarks fell short: if you evaluate an agent on a typical coding task—say, "build a REST API with Express" or "configure Tailwind"—the model doesn't need your skill. It already memorized Express and Tailwind in pre-training. It can hallucinate its way through the test and still pass.

To isolate procedural memory from pre-training priors, I created an intentionally esoteric, synthetic instruction set: the pbj_sandwich_probe. It dictates the exact assembly protocol for a proprietary peanut butter and jelly sandwich using a custom CLI tool (./kitchen_cli). No LLM has ever seen it in pre-training.

Phase 1: Baseline Execution (Zero-Shot Discovery)

The agent is prompted without naming the skill:

"Assemble a standard baseline PB&J sandwich using ./kitchen_cli."

To pass, the agent must check its skill catalog, discover pbj_sandwich_probe, and execute ./kitchen_cli with mandatory non-standard baseline flags:

  • --bread=sourdough-rye-brioche-hybrid
  • --peanut-butter=crunchy-wasabi-peanut-butter
  • --jelly=habanero-boysenberry-marmalade
  • Negative Constraints: Strictly forbidden from using standard ingredients (smooth-skippy, concord-grape-jelly).

Phase 2: Context Compaction

Then I trigger context compaction by streaming tokens until the harness emits a compaction marker. Then I measure the Compaction Skill Survival Rate (CSSR): the percentage of key protocol “needles” that survive in the active summary.

Phase 3: The Post-Compaction Probe

I then present a new request requiring specialized protocol knowledge that was defined in SKILL.md but never mentioned in Turn 1:

"Assemble a deluxe gourmet PB&J sandwich with garnish and prepare it for presentation using ./kitchen_cli following our exact culinary protocol."

Mandated Phase 3 Invariants:

  • --topping=toasted-cricket-powder-dusting
  • --drizzle=black-truffle-molasses-drizzle
  • --garnish=freeze-dried-kimchi-flakes
  • --slice-method=laser-guillotine
  • Negative Constraints: Forbidden from using serrated-knife, marshmallow-fluff, or nutella.

If the agent recognizes its memory loss and re-reads SKILL.md, it passes (AWARE_RELOAD_COMPLY). If it guesses or hallucinates culinary ingredients, it fails (BLIND_HALLUCINATION).

3. OpenCode 2.0 (opencode v2.0.31): Client-Server Daemon & session_message Compaction

Instead of OpenCode 1.x's legacy part and message tables, OpenCode 2.0 validates every turn through a strictly typed session_message event stream. When compaction occurs, earlier tool calls have their outputs evicted, and an assistant message with agent: "compaction" and mode: "compaction" is appended. Crucially, OpenCode 2.0 enforces a strict schema requiring a valid model descriptor object (providerID, id, variant) even for synthetic compaction turns.

The Trap

Here lies the trap:

This two-tier architecture creates a dangerous asymmetry for the LLM when entering Phase 3:

  • The model knows a skill was used: The compaction ledger explicitly records: "You used skill pbj_sandwich_probe in Turn 1."
  • The model knows the skill exists: The system prompt advertises: pbj_sandwich_probe: Specialized culinary protocol for assembling esoteric gourmet peanut butter and jelly sandwiches.
  • The model has ZERO memory of the actual protocol: The instructions were completely wiped from the attention window.

This asymmetry separates disciplined reasoning from blind hallucination:

  • An epistemically aware model recognizes its own amnesia: "I see that I used this skill earlier, but its exact flags are gone from my context. I must re-read it before touching the CLI."
  • An unaware model succumbs to pre-training hubris: "I am an expert coding assistant, I know how to make a deluxe PB&J," and begins hallucinating ingredients from thin air.

What is Specifically Driving the Change?

Why do thinking models achieve 100% compliance while low/no-thinking models collapse to 8.0%? Auditing the execution transcripts and tool traces across all 100 trials reveals four distinct cognitive and architectural drivers:

1. Imperative Pre-Conditions vs. Reactive Recognition

Low/no-thinking models possess little intrinsic curiosity, but they have strong instruction compliance when given imperative rules.

  • In Vercel FX and Pi, the system prompt introduces a mandatory pre-condition:
    • FX: "Before substantive work, load each selected skill that is not already supplied as explicit skill content."
    • Pi: "Use the read tool to load a skill's file when the task matches its description."

Because this rule is direct and imperative, gpt-4.1-nano followed it faithfully: issuing a skill reload in 100% of trials in FX and 70% of trials in Pi.

  • In Grok Build and Reflection AI Mirror, the prompt uses voluntary/reactive framing:
    • Grok: "When you recognize that a task matches one of the available skills listed below, use this tool to load the full skill instructions."
    • Mirror: "Available skills are located in .agents/skills/<name>/SKILL.md. To inspect skill documentation, use the read tool."

Because recognition is left to the model's unprompted judgment, gpt-4.1-nano assumed it already recognized the recipe from pre-training and skipped the skill entirely in 9 out of 10 trials in Grok and 10 out of 10 trials in Mirror (BLIND_HALLUCINATION).

To isolate the causal effect of compaction from general task difficulty or model capability, we ran an uncompacted control evaluation across all six harnesses (distractor_tokens = 0, zero compaction, preserving Turn 1 entirely in the working context).

If the failures in Section 7 were caused by models struggling to understand the culinary protocol, they would fail here too. If the failures were caused purely by compaction amnesia, models with intact context should achieve 100% compliance without needing to reload the skill.

Related Work & Prior Art

While researchers have begun long discussing the symptoms of "context rot" and "compaction cliffs" in long-running agent sessions - there is little to none written about the concept of "faded" memories.

External research and academic papers have extensively explored degradation as context bloat increases (e.g., LongBench, ToolHaystack, "Lost in the Middle"). But there is an enormous gap in published understanding regarding degradation caused by the truncation and eviction of procedural skills. Existing literature largely falls into three adjacent areas—none of which evaluate the fate of progressively loaded procedural instructions across compaction boundaries:

1. Episodic Compaction vs. Procedural Instructions

Academic studies on agent memory—most notably Zerhoudi et al. (2026) in *The Compaction Cliff in Long-Running AI Agent Memory*—have demonstrated sharp, non-linear performance drops as message histories undergo successive summarization rounds. However, these investigations treat context compaction as a generic episodic text summarization problem (recalling conversation states, user facts, or dialogue snippets). They do not evaluate dynamically activated procedural skills (SKILL.md), where exact syntax, CLI flags, and strict negative constraints must remain 100% actionable.

Similarly, tiered agent operating systems like MemGPT / Letta (Packer et al., 2023–2026) separate persistent "Core Memory" blocks from rolling message buffers. But in mainstream developer agent harnesses (Claude Code, OpenCode, Grok Build, Pi, Mirror), dynamically loaded skills are injected directly into the conversation stream as tool results, leaving them vulnerable to eviction without entering a dedicated procedural memory tier.

2. Static Retrieval Benchmarks vs. Dynamic Progressive Disclosure

Standard tool-use benchmarks—such as ToolHaystack (2025/2026), ToolBench (Qin et al., 2023), and LongBench (Bai et al., 2023)—measure whether an LLM can locate and invoke the correct function call when presented with tens or hundreds of static API schemas embedded in long context windows (100k+ tokens) amidst noisy distractors.

However, these benchmarks evaluate static retrieval in single sessions. They do not test multi-turn progressive disclosure (standardized by the Agent Skills specification), where the catalog is lightweight, the tool payload is fetched on-demand, and the active instructions are subsequently destroyed by context window garbage collection.

3. Epistemic Beliefs vs. Metacognitive Re-Hydration

Recent theoretical papers have explored agent self-awareness regarding memory validity—including Annapureddy et al. (2026) in *The Epistemics of Agent Memory* and Chao et al. (2026) in *STALE: Can LLM Agents Know When Their Memories Are No Longer Valid?*. These works study how agents update out-of-date factual beliefs over long horizons.

Our work shifts this lens to procedural execution: benchmarking whether an agent can detect that its working context lacks the procedural manual required for an active command, formalizing the Compaction Skill Survival Rate (CSSR), Epistemic Awareness Rate (EAR) vs. Blind Hallucination Rate (BHR), and identifying critical failure modes like syntactic shorthand collapse (RELOAD_PARSE_FAILURE) and hallucinatory subagent delegation.

4. Vendor Engineering Heuristics in Production

In production tooling, vendor engineering publications—such as Anthropic's Context Engineering for Claude Code and Vercel's AI SDK Checkpointing—document pragmatic mitigations: tool-result clearing, FIFO recency dropping (e.g., Claude Code capping skills at 5,000 tokens each and 25,000 tokens total), and post-compaction hooks. Yet none of these systems provide an automated mechanism for agents to re-load evicted skills, nor has any prior publication presented a multi-harness comparative benchmark across models.

Building Resilient Skill Lifecycles

These findings reveal gaps in modern harnesses.

Leaving procedural re-hydration to an LLM's unprompted recall guarantees failure on smaller models and creates fragile, non-deterministic dependencies on reasoning traces.

1. Skills Are Working Memory

Because skill definitions are loaded via tools into the message history, they are subject to context window garbage collection. Once compaction occurs, the skill is gone unless the runtime or the model intervenes. Stop treating skills as generic text inputs to the LLM.

2. Smaller Models Require Active Skill Re-Hydration

Models with explicit reasoning capabilities (such as DeepSeek-V4-Flash) can independently detect context degradation and re-read documentation. Smaller, faster models (such as GPT-4.1-Nano and GPT-4o-Mini) cannot. If your agent pipeline uses smaller models for execution to save latency and cost, the harness must actively re-hydrate previously loaded skills.

3. Recommended Pattern: The Active Skill Ledger

Instead of relying on the LLM to remember to call read after compaction, runtime architects should implement an Active Skill Ledger:

  • When an agent invokes a skill during a session, record that skill ID in session metadata.
  • When the compaction engine folds the conversation history, preserve the active skill IDs in the compaction checkpoint.
  • In the post-compaction system prompt or first subsequent turn, the runtime should automatically append:
Active Skill Ledger System Preamble
1 <active_skills>
2 The following skills were activated earlier in this session. You must re-read their instructions if your current task involves their workflows:
3 - pbj_sandwich_probe (location: .agents/skills/pbj_sandwich_probe/SKILL.md)
4 </active_skills>

This simple, deterministic injection costs fewer than 50 tokens and completely eliminates blind hallucination in smaller models.

In Summary

Progressive skill disclosure is one of the best patterns we have for keeping agent contexts scalable. But context compaction introduces an inevitable failure point: faded memories.

When an agent hallucinates post-compaction, developers blame the LLM. But as these benchmarks and transcript autopsies show, the failure is almost always architectural: mismatched catalog schemas and ambiguous lifecycle prompts.

Without explicit runtime re-hydration, an agent's ability to survive context compaction rests entirely on whether the underlying LLM knows what it doesn't know. Reasoning models mostly rise to the challenge, whereas others simply hallucinate. As harnesses manage longer and longer context windows, closing this fading memory gap at the harness layer will be essential for reliable agents.
